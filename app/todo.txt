 1. O QUE ESTÁ A FUNCIONAR (100%)
═══════════════════════════════════════════════════════════════════════════════

  ✅ MQTT (Mosquitto)
     · Broker com autenticação (simulador + backend, users separados)
     · ACLs configuradas
     · Backend subscreve "motoguard/telemetria", publica em "motoguard/comando"
     · Ficheiros: mqtt.service.ts, docker/mosquitto/*

  ✅ Simulador Python (headless_simulator.py)
     · Gera telemetria realista a 1 msg/s
     · 8 perfis de moto (Scooter, Naked, Desportiva, etc.)
     · Publica JSON via MQTT, recebe comandos (definir_modelo, parar, etc.)
     · Funciona no Docker sem GUI

  ✅ Validação de Telemetria
     · validate-telemetry.ts valida 6 blocos: telemetry, imu, active_safety,
       health, location, system
     · Rejeita payloads mal formados antes de processar

  ✅ InfluxDB — Escrita de Telemetria
     · influx.service.ts escreve 17 campos por ponto (speed, rpm, imu, gps, etc.)
     · Flush em lote (20 pontos ou 5s)
     · Tags: device_id, moto_model

  ✅ InfluxDB — Leitura de Telemetria
     · queryTripTelemetry() faz query Flux por intervalo de tempo + device_id
     · Endpoint: GET /api/telemetry/:tripId (protegido por JWT)

  ✅ Socket.IO — Tempo Real
     · Reencaminha telemetria MQTT → frontend via WebSocket
     · Emite eventos: telemetry_update, alert, trip_started, trip_ended
     · Recebe comandos do frontend e reencaminha para MQTT

  ✅ Frontend React — Dashboard
     · 6 componentes: GaugeCard, TempVoltCard, IMUCard, MapCard, StatusCard,
       CommandPanel
     · Mapa GPS com Leaflet (marcador + trilho de rota)
     · Painel de comandos (definir_modelo, arrancar, parar)
     · Log de eventos em tempo real

  ✅ REST API — Endpoints Públicos
     · GET /api/health — estado do backend (MQTT, stats, infra)
     · GET /api/telemetry/latest — última leitura em memória
     · POST /api/command — enviar comando ao simulador via MQTT

  ✅ Docker Compose — Orquestração
     · 6 serviços: mosquitto, influxdb, postgres, backend, simulador, frontend
     · Rede interna motoguard-net, volumes persistentes

 2. CÓDIGO IMPLEMENTADO MAS NÃO LIGADO AO FLUXO PRINCIPAL
═══════════════════════════════════════════════════════════════════════════════

  ⚠️  PRISMA + POSTGRESQL — Parcialmente Integrado

     O que EXISTE e está escrito:
     ──────────────────────────
     · Schema completo (schema.prisma): 5 modelos
       - User (email, password, name)
       - MotorcycleProfile (8 perfis com thresholds de deteção)
       - Motorcycle (ligada a user + profile)
       - Trip (viagens com stats: distância, velocidade, inclinação)
       - TripEvent (eventos de risco: queda, travagem brusca, etc.)
     · Prisma Client gerado (src/generated/prisma/)
     · Prisma Service singleton (prisma.service.ts)
     · Migrations criadas (2 migrations SQL)
     · Seed com os 8 perfis de moto (seed.ts)
     · prisma.config.ts configurado

     O que ESTÁ LIGADO ao backend:
     ─────────────────────────────
     · index.ts faz prisma.$connect() no arranque (verifica conexão)
     · index.ts faz prisma.$disconnect() no shutdown graceful
     · health.controller.ts verifica se DATABASE_URL está configurado

     Controllers que USAM Prisma (código escrito, rotas registadas):
     ───────────────────────────────────────────────────────────────
     · auth.controller.ts — register + login com bcrypt + JWT
       Rotas: POST /api/auth/register, POST /api/auth/login
       → prisma.user.create(), prisma.user.findUnique()

     · motorcycle.controller.ts — CRUD de motas
       Rotas: POST /api/motorcycles, GET /api/motorcycles,
              GET /api/motorcycle-profiles
       → prisma.motorcycle.create(), prisma.motorcycle.findMany(),
         prisma.motorcycleProfile.findMany()

     · trip.controller.ts — Listar/detalhar viagens
       Rotas: GET /api/trips, GET /api/trips/:id
       → prisma.trip.findMany(), prisma.trip.findFirst()

     · telemetry.controller.ts — getTripTelemetry usa Prisma para
       verificar que a trip pertence ao user antes de consultar InfluxDB
       → prisma.trip.findFirst(), prisma.motorcycle.findFirst()

     · auth.middleware.ts — Middleware JWT (verifica token, extrai userId)

     O que FALTA para funcionar de verdade:
     ──────────────────────────────────────
     □ Migrations não são executadas automaticamente no Docker
       (Dockerfile faz prisma generate mas NÃO faz prisma migrate deploy)
     □ Seed nunca é executado automaticamente
     □ Nenhum dos endpoints de auth/motorcycles/trips é chamado pelo frontend
       (o dashboard não tem UI de login, registo, ou gestão de motas/viagens)
     □ Trips não são criadas automaticamente quando o simulador "inicia viagem"
       (socket.service.ts emite trip_started/trip_ended mas não persiste no PostgreSQL)
     □ TripEvents não são gerados a partir dos alertas detetados

 4. PROBLEMAS / DÍVIDA TÉCNICA
═══════════════════════════════════════════════════════════════════════════════

  🔴 Migrations NÃO executam no Docker
     · O Dockerfile faz "npx prisma generate" mas NÃO faz "npx prisma migrate deploy"
     · Resultado: as tabelas (users, motorcycles, trips, trip_events,
       motorcycle_profiles) provavelmente NÃO existem no PostgreSQL
     · Fix: Adicionar ao Dockerfile ou ao CMD do container:
       npx prisma migrate deploy

  🔴 Trips não são persistidas no PostgreSQL
     · socket.service.ts deteta trip_started/trip_ended por velocidade
     · Emite eventos Socket.IO mas NÃO cria registos na BD
     · Para ligar: chamar prisma.trip.create() quando trip_started e
       prisma.trip.update() quando trip_ended

  🔴 Alertas não são persistidos como TripEvents
     · socket.service.ts deteta alertas (CRASH, OVERHEAT, etc.)
     · Emite "alert" via Socket.IO mas NÃO grava na BD
     · Para ligar: chamar prisma.tripEvent.create() quando alerta detetado

  🟡 Backend dist/ fica desatualizado
     · Editar ficheiros em src/ não atualiza dist/ automaticamente
     · O Docker faz "npm run build" (recompila tudo) — OK em Docker
     · Mas em desenvolvimento local, se correr dist/ diretamente vai ter
       código antigo

  🟡 Simulador GUI (motoguard_simulator.py) pode ter diferenças do headless
     · O headless é o que corre no Docker
     · O GUI é para desenvolvimento local — garantir que estão sincronizados

  🟡 Frontend não tem páginas de Auth/Gestão
     · Só existe o dashboard de telemetria em tempo real
     · Não há login, registo, gestão de motas, ou histórico de viagens
